  • Incluye consulta pública y validación de credenciales para comercios adheridos.
  • Deja aprobada una V2 para productos, pedidos, stock y contabilidad.

1

Visión del producto

Nombre

Uni2

Descripción

Uni2 es una plataforma de gestión para mutuales escolares. Inicialmente será utilizada por la mutual del CET 3, pero el modelo queda preparado para soportar más colegios en el futuro.

El sistema permitirá administrar

  • Asociados y adherentes.
  • Colegios, cursos e historial escolar.
  • Cuotas y pagos.
  • Credenciales digitales.
  • Beneficios institucionales.
  • Comercios adheridos con su beneficio comercial.
  • Reportes administrativos básicos.
  • Contabilidad simple con asientos y partidas.

En versiones futuras incorporará

  • Productos.
  • Pedidos.
  • Stock.
  • Pagos de pedidos.
  • Tickets de consultas.
  • Notificaciones push.
  • Pago online.
  • Contabilidad ampliada.
  • Mapa de comercios.

2

Roles

Visitante

Usuario no autenticado. Puede consultar:

  • Página de inicio.
  • Información institucional.
  • Beneficios.
  • Comercios adheridos.
  • Acceso al login.

Asociado

Usuario autenticado vinculado a un asociado o adherente. Puede:

  • Ver su panel.
  • Ver su credencial digital.
  • Ver estado de cuotas.
  • Consultar beneficios.
  • Consultar comercios adheridos.

Administrador

Usuario interno de gestión. Puede:

  • Gestionar asociados e importarlos.
  • Crear usuarios para asociados.
  • Gestionar colegios y cursos.
  • Gestionar cuotas y registrar pagos.
  • Gestionar beneficios.
  • Gestionar comercios.
  • Consultar reportes.
  • Registrar o consultar asientos simples.

Comercio

Usuario vinculado a un comercio adherido. Puede:

  • Iniciar sesión.
  • Validar credenciales.
  • Consultar su beneficio vigente.

4

Modelo de datos MVP

Usuario

Usuario de autenticación de Django. Se recomienda usar el sistema estandar inicialmente.

Grupos sugeridos: Administradores, Asociados, Comercios.

Campos relevantes: username, email, password, first_name, last_name, is_active, is_staff, last_login, date_joined.

Colegio

Representa una institución educativa.

Campos:

  • id
  • nombre
  • direccion
  • teléfono
  • email
  • activo

Notas: inicialmente existirá CET 3 y se incluye desde el inicio para dejar preparado el sistema para otros colegios.

Curso

Representa un curso de un colegio.

Campos:

  • id
  • colegio
  • nombre
  • activo

Ejemplos: 1° 1°, 1° 2°, 3° 2°, 5° 1°.

Relación: Colegio 1 a N Curso.

Asociado

Representa a una persona asociada o adherente a la mutual.

Campos:

  • id
  • usuario
  • nombre
  • apellido
  • dni
  • email
  • teléfono
  • fecha_nacimiento
  • tipo
  • número_asociado
  • token_credencial
  • curso_actual
  • estado
  • fecha_alta
  • fecha_inicio_cobro
  • fecha_baja
  • motivo_baja

Tipos: asociado, adherente.

Estados: activo, inactivo, egresado.

Reglas: DNI obligatorio y único, número automático, token UUID único, usuario opcional, curso actual opcional para adherentes y recomendado para asociados alumnos.

InscripciónCurso

Historial académico del asociado.

Campos:

  • id
  • asociado
  • curso
  • ciclo_lectivo
  • activa
  • fecha_desde
  • fecha_hasta

Reglas: puede haber varias inscripciones históricas, solo una activa por ciclo lectivo, al cambiar de año se crea una nueva inscripción, incluso si repite curso.

Ejemplo: Juan Pérez - 2026 - 3° 2° - no activa / Juan Pérez - 2027 - 4° 2° - activa.

PeríodoCuota

Representa un período mensual de cuota.

Campos:

  • id
  • mes
  • año
  • importe
  • importe_recargo_mora
  • fecha_vencimiento
  • activo

Reglas: define importe base y recargo fijo por mora, y ambos deben copiarse a la cuota generada para conservar historial. Cambios futuros no deben afectar cuotas ya generadas.

Ejemplo: Mayo 2026 - $3000 - vence 10/05/2026.

Cuota

Representa una cuota concreta de un asociado para un período.

Campos:

  • id
  • asociado
  • período
  • importe
  • importe_recargo_mora
  • importe_pagado
  • estado
  • fecha_generación

Estados: pendiente, parcial, pagada, vencida, bonificada.

Restricción: no puede existir más de una cuota para el mismo asociado y período.

Reglas: si importe_pagado es 0 puede estar pendiente o vencida; si es parcial queda parcial; si alcanza el importe queda pagada; si se bonifica queda bonificada; vencida exige importe + importe_recargo_mora.

Pago

Representa un ingreso de dinero.

Campos:

  • id
  • asociado
  • fecha
  • importe
  • método
  • observaciones
  • registrado_por

Métodos: efectivo, billetera_virtual.

Reglas: en el MVP se usa para pagos de cuotas; en V2 podrá aplicarse también a pedidos mediante PagoPedido.

PagoCuota

Aplicación de un pago a una cuota.

Campos:

  • id
  • pago
  • cuota
  • importe

Reglas: permite saber que cuotas fueron cubiertas por cada pago, soporta pagos parciales, un pago puede aplicarse a varias cuotas y una cuota puede tener varios pagos parciales.

Ejemplo: pago de $6000 distribuido entre cuota marzo $3000 y cuota abril $3000.

Beneficio

Beneficio institucional de la mutual.

Campos:

  • id
  • título
  • descripción
  • activo
  • orden

ActividadComercial

Clasifica el rubro o actividad principal de un comercio adherido.

Campos:

  • id
  • nombre

Comercio

Comercio adherido a la mutual.

Campos:

  • id
  • actividad_comercial
  • usuario
  • nombre
  • propietario
  • beneficio_texto
  • estado
  • fecha_convenio
  • notas
  • flyer_disponible
  • email
  • teléfono
  • dirección
  • url_presencia_web
  • ciudad
  • provincia
  • latitud
  • longitud

Estados: pendiente, firmado, vencido, baja.

Reglas: puede tener usuario de acceso, validar credenciales si su estado es firmado, informar una URL pública, guardar un único beneficio como texto libre, usar una actividad comercial definida y guardar coordenadas para mapa futuro.

Relaciones del MVP

  • Colegio 1 - N Curso
  • Usuario 1 - 0..1 Asociado
  • Curso 1 - N Asociado como curso_actual
  • Asociado 1 - N InscripcionCurso
  • Curso 1 - N InscripcionCurso
  • PeríodoCuota 1 - N Cuota
  • Asociado 1 - N Cuota
  • Asociado 1 - N Pago
  • Pago 1 - N PagoCuota
  • Cuota 1 - N PagoCuota
  • ActividadComercial 1 - N Comercio
  • Usuario 1 - 0..1 Comercio

6

Reglas de negocio

Asociados

  • ASOCIADO-001 Un asociado puede ser de tipo asociado o adherente.
  • ASOCIADO-002 Los asociados participan de asambleas; los adherentes no.
  • ASOCIADO-003 Los asociados inactivos o egresados conservan su historial.
  • ASOCIADO-004 Solo los asociados activos generan nuevas cuotas.
  • ASOCIADO-005 Todo asociado debe tener DNI.
  • ASOCIADO-006 No puede existir más de un asociado con el mismo DNI.
  • ASOCIADO-007 El número de asociado debe generarse automáticamente.
  • ASOCIADO-008 Un asociado puede existir sin usuario de acceso.

Cursos

  • CURSO-001 El curso actual se guarda en Asociado para simplificar consultas.
  • CURSO-002 El historial de curso se guarda en InscripcionCurso.
  • CURSO-003 Cuando un alumno cambia de curso, se crea una nueva InscripcionCurso y se actualiza curso_actual.
  • CURSO-004 Si un alumno repite, igualmente se crea una nueva InscripcionCurso para el nuevo ciclo lectivo.

Altas de asociado

  • ALTA-ASOCIADO-001 Si el alta ocurre antes del día 15, el asociado paga el mes actual.
  • ALTA-ASOCIADO-002 Si el alta ocurre después del día 15, comienza a pagar desde el mes siguiente.
  • ALTA-ASOCIADO-003 La fecha de alta y la fecha de inicio de cobro son independientes. El sistema debe usar fecha_inicio_cobro para generar cuotas.

Cuotas

  • CUOTA-001 No puede existir más de una cuota por asociado y período.
  • CUOTA-002 Cada cuota almacena su propio importe.
  • CUOTA-003 Una cuota puede estar pendiente, parcial, pagada, vencida o bonificada.
  • CUOTA-004 Se generan cuotas para asociados activos cuya fecha_inicio_cobro sea menor o igual al período generado.
  • CUOTA-005 Si la cuota ya existe para el asociado y período, no debe generarse otra.
  • CUOTA-006 Si al vencimiento la cuota no esta totalmente cancelada, se aplica un recargo fijo por mora una sola vez.
  • CUOTA-007 El recargo por mora debe copiarse desde PeríodoCuota a Cuota al momento de generarla.

Pagos

  • PAGO-001 Los pagos se aplican a la deuda más antigua primero.
  • PAGO-002 Se permiten pagos parciales de cuotas.
  • PAGO-003 No se permite registrar un pago mayor que la deuda seleccionada.
  • PAGO-004 Si el pago se registra después del vencimiento y la cuota no estaba cancelada, la deuda exigible incluye el recargo fijo por mora.
  • PAGO-005 Un pago puede aplicarse a varias cuotas mediante PagoCuota.
  • PAGO-006 Los métodos permitidos en MVP son efectivo y billetera_virtual.

Usuarios

  • USUARIO-001 Crear asociado no crea automáticamente un usuario.
  • USUARIO-002 El administrador puede crear un usuario para un asociado existente.
  • USUARIO-003 No se puede crear un nuevo usuario para un asociado que ya tiene uno vinculado.
  • USUARIO-004 El username puede ser el DNI.
  • USUARIO-005 El listado de asociados debe mostrar si tiene usuario y el ultimo acceso usando User.last_login.

Comercios

  • COMERCIO-001 Cada comercio tiene una única actividad comercial vinculada mediante ActividadComercial.
  • COMERCIO-002 El beneficio del comercio se guarda como texto libre dentro de Comercio.
  • COMERCIO-003 El estado del comercio se selecciona desde una lista fija definida en el sistema. No se administra como entidad independiente.
  • COMERCIO-004 Solo comercios con estado firmado pueden validar credenciales.

Credenciales

  • CREDENCIAL-001 Solo asociados activos poseen credenciales válidas.
  • CREDENCIAL-002 La credencial debe validarse con un token UUID aleatorio y no debe exponer IDs internos ni correlativos en URLs o QR.
  • CREDENCIAL-003 Si el token no existe o no es valido, debe mostrarse credencial inválida.
  • CREDENCIAL-004 El comercio solo debe ver válida/inválida, nombre y apellido, tipo y estado. No debe ver deuda ni datos sensibles.

7

Casos de uso MVP

CU-consultar-sitio-publico

Actor: Visitante

Flujo principal:

  1. Ingresa al sitio.
  2. Consulta información institucional.
  3. Revisa beneficios y comercios.

Modelos afectados: Beneficio, ActividadComercial, Comercio.

CU-ver-credencial

Actor: Asociado

Flujo principal:

  1. Inicia sesión.
  2. Entra a Mi Credencial.
  3. El sistema muestra la credencial digital con QR.

Reglas relacionadas: CREDENCIAL-001, CREDENCIAL-002.

Modelos afectados: Asociado, Usuario.

CU-ver-estado-cuotas

Actor: Asociado

Flujo principal:

  1. Inicia sesión.
  2. Entra a Mis Cuotas.
  3. Visualiza cuotas pagadas, parciales, pendientes y vencidas.

Reglas relacionadas: CUOTA-001, CUOTA-002, CUOTA-003.

Modelos afectados: Cuota, PeríodoCuota, PagoCuota.

CU-crear-asociado

Actor: Administrador

Flujo principal:

  1. Carga datos personales.
  2. Selecciona tipo y curso si corresponde.
  3. Define fecha de alta.
  4. Calcula o ajusta fecha_inicio_cobro.
  5. Guarda el asociado.
  6. Crea InscripcionCurso si aplica.

Reglas relacionadas: ASOCIADO-001, ASOCIADO-005, ASOCIADO-006, ASOCIADO-007, ALTA-ASOCIADO-001, ALTA-ASOCIADO-002, ALTA-ASOCIADO-003.

Situaciones especiales: DNI duplicado, curso inexistente, alta después del día 15, asociado sin usuario.

Modelos afectados: Asociado, Curso, InscripcionCurso.

CU-importar-asociados

Actor: Administrador

Flujo principal:

  1. Sube archivo Excel/CSV.
  2. El sistema valida columnas, DNI, tipo y curso.
  3. Informa errores y advertencias.
  4. Se confirma la importación.
  5. Se crean asociados e inscripciones.

Reglas relacionadas: ASOCIADO-005, ASOCIADO-006, ASOCIADO-007, CURSO-001, CURSO-002.

Situaciones especiales: DNI duplicado, curso inexistente, asociado ya existente, email faltante, teléfono faltante, tipo invalido.

Modelos afectados: Asociado, Curso, InscripcionCurso.

CU-crear-usuario-asociado

Actor: Administrador

Flujo principal:

  1. Busca asociado.
  2. Verifica que no tenga usuario.
  3. Crea User.
  4. Lo vincula con Asociado.
  5. Lo agrega al grupo Asociados.

Reglas relacionadas: USUARIO-001, USUARIO-002, USUARIO-003, USUARIO-004.

Situaciones especiales: asociado ya posee usuario, DNI inexistente, username duplicado, email vacío.

Modelos afectados: User, Asociado.

CU-generar-periodo-cuota

Actor: Administrador

Flujo principal:

  1. Crea PeríodoCuota con mes, año, importe y vencimiento.
  2. Ejecuta generación de cuotas.
  3. El sistema genera para asociados activos alcanzados por fecha_inicio_cobro.
  4. Evita duplicados.

Reglas relacionadas: ASOCIADO-004, CUOTA-001, CUOTA-002, CUOTA-004, CUOTA-005.

Situaciones especiales: asociado inactivo, egresado, fecha_inicio_cobro posterior, cuota ya generada.

Modelos afectados: PeríodoCuota, Cuota, Asociado.

CU-registrar-pago-cuota

Actor: Administrador

Flujo principal:

  1. Busca asociado.
  2. Visualiza deuda.
  3. Ingresa importe y método.
  4. El sistema aplica el pago a la deuda más antigua.
  5. Actualiza la cuota.
  6. Crea PagoCuota.
  7. Puede generar Asiento.

Reglas relacionadas: PAGO-001, PAGO-002, PAGO-003, PAGO-005, PAGO-006.

Situaciones especiales: pago parcial, exacto, para múltiples cuotas, pago mayor a deuda, asociado sin deuda.

Modelos afectados: Pago, PagoCuota, Cuota, Asiento.

CU-dar-baja-asociado

Actor: Administrador

Flujo principal:

  1. Busca asociado.
  2. Selecciona baja.
  3. Carga fecha y motivo.
  4. El sistema cambia el estado a inactivo.
  5. Conserva cuotas, pagos e historial.

Reglas relacionadas: ASOCIADO-003, ASOCIADO-004.

Situaciones especiales: baja con deuda, baja sin deuda, asociado con usuario.

Modelos afectados: Asociado.

CU-marcar-asociado-egresado

Actor: Administrador

Flujo principal:

  1. Busca asociado.
  2. Cambia el estado a egresado.
  3. El sistema conserva el historial.
  4. Deja de generar nuevas cuotas.

Reglas relacionadas: ASOCIADO-003, ASOCIADO-004.

Modelos afectados: Asociado, InscripcionCurso.

CU-cambiar-curso

Actor: Administrador

Flujo principal:

  1. Busca asociado.
  2. Selecciona nuevo curso y ciclo lectivo.
  3. El sistema desactiva la inscripción anterior si corresponde.
  4. Crea una nueva inscripción.
  5. Actualiza curso_actual.

Reglas relacionadas: CURSO-001, CURSO-002, CURSO-003, CURSO-004.

Situaciones especiales: promoción normal, repite curso, cambio de división.

Modelos afectados: Asociado, Curso, InscripcionCurso.

CU-validar-credencial

Actor: Comercio

Flujo principal:

  1. Escanea el QR o ingresa el token.
  2. El sistema busca al asociado por token_credencial.
  3. Verifica el estado.
  4. Muestra el resultado.

Reglas relacionadas: COMERCIO-004, CREDENCIAL-001, CREDENCIAL-002, CREDENCIAL-003, CREDENCIAL-004.

Situaciones especiales: QR invalido, asociado inactivo, asociado egresado, comercio inactivo.

Modelos afectados: Asociado, Comercio.

CU-gestionar-comercio

Actor: Administrador

Flujo principal:

  1. Crea o edita el comercio.
  2. Selecciona la actividad comercial.
  3. Carga el beneficio como texto libre.
  4. Define el estado.
  5. Carga datos de contacto.
  6. Carga dirección.
  7. Carga coordenadas opcionales.
  8. Define el estado del convenio.

Reglas relacionadas: COMERCIO-001, COMERCIO-002, COMERCIO-003, COMERCIO-004.

Situaciones especiales: comercio sin convenio firmado, beneficio no cargado, actividad comercial no definida.

Modelos afectados: ActividadComercial, Comercio.

8

Casos borde y situaciones especiales

CB-alta-mitad-mes

Situación: el alta ocurre cerca del cierre del período mensual.

Respuesta esperada: si ocurre antes del día 15, paga el mes actual; si ocurre después del día 15, comienza a pagar desde el mes siguiente. El administrador puede ajustar fecha_inicio_cobro.

Caso de uso relacionado: CU-crear-asociado.

Relacionado con: ALTA-ASOCIADO-001, ALTA-ASOCIADO-002, ALTA-ASOCIADO-003.

CB-asociado-sin-usuario

Situación: el asociado existe en el padrón, pero todavía no tiene usuario vinculado.

Respuesta esperada: la situación es válida. El asociado queda cargado, pero no puede iniciar sesión hasta que se cree su User.

Caso de uso relacionado: CU-crear-asociado, CU-crear-usuario-asociado.

Relacionado con: ASOCIADO-008, USUARIO-001.

CB-usuario-desactivado

Situación: existe un asociado activo con usuario desactivado.

Respuesta esperada: se bloquea el acceso, pero no se borran ni alteran los datos del asociado.

Caso de uso relacionado: CU-ver-credencial, CU-ver-estado-cuotas.

Relacionado con: USUARIO-005.

CB-cambio-curso

Situación: un asociado cambia de curso o división.

Respuesta esperada: no se pisa el historial. Se crea una nueva InscripcionCurso y se conserva la anterior.

Caso de uso relacionado: CU-cambiar-curso.

Relacionado con: CURSO-002, CURSO-003.

CB-repite-curso

Situación: el asociado repite curso en un nuevo ciclo lectivo.

Respuesta esperada: aunque el curso sea el mismo, se crea una nueva InscripcionCurso para ese nuevo ciclo.

Caso de uso relacionado: CU-cambiar-curso.

Relacionado con: CURSO-004.

CB-baja-con-deuda

Situación: se da de baja a un asociado que mantiene deuda.

Respuesta esperada: la baja está permitida. La deuda se conserva y no se generan nuevas cuotas.

Caso de uso relacionado: CU-dar-baja-asociado.

Relacionado con: ASOCIADO-003, ASOCIADO-004.

CB-egresado-con-deuda

Situación: un asociado pasa a estado egresado y mantiene deuda.

Respuesta esperada: está permitido. La deuda se conserva y no se generan nuevas cuotas.

Caso de uso relacionado: CU-marcar-asociado-egresado.

Relacionado con: ASOCIADO-003, ASOCIADO-004.

CB-cuota-ya-generada

Situación: se intenta generar una cuota para un asociado y período que ya existen.

Respuesta esperada: el sistema no genera duplicados.

Caso de uso relacionado: CU-generar-periodo-cuota.

Relacionado con: CUOTA-001, CUOTA-005.

CB-pago-parcial

Arquitectura actual del código

El código está organizado por dominio de negocio y por experiencia de usuario. La separación vigente busca que la app usuarios se ocupe de autenticación y roles, mientras que la app gestion concentra el backoffice usado por personal interno.

Apps principales

  • usuarios: login, logout, helpers de roles y navegación.
  • gestion: dashboard interno, cobros, deudores, asociados y períodos de cuota.
  • asociados: experiencia del asociado autenticado y su dominio.
  • comercios: validación y panel del comercio adherido.
  • cuotas: modelos y servicios de cuotas, deuda y pagos.
  • web: home y páginas públicas del sitio.
  • contenidos: beneficios publicados por la web.
  • contabilidad: cuentas y asientos simples.

Criterio de separación

  • Las apps representan dominios de negocio o contextos técnicos bien delimitados.
  • La carpeta templates/gestion/ contiene pantallas de operación para usuarios staff.
  • La carpeta templates/asociados/ contiene el panel y vistas del asociado.
  • La carpeta templates/comercios/ contiene el flujo del comercio.
  • La carpeta templates/web/ agrupa el sitio público.
  • El admin de Django queda como soporte técnico y no como navegación principal del backoffice.

Dashboards y entradas

  • Staff interno: dashboard de gestion.
  • Asociado autenticado: dashboard de asociados.
  • Comercio autenticado: dashboard de comercios.
  • Luego del login, el sistema redirige según el rol y el perfil vinculado.
  • La navegación para staff prioriza el acceso al backoffice propio y deja el admin de Django como herramienta técnica complementaria.

Objetivo de la app gestión

  • Evitar que tareas frecuentes dependan del admin genérico de Django.
  • Ofrecer pantallas operativas orientadas a flujo: cobrar, buscar asociado, ver deudores, administrar cuotas.
  • Permitir una UX propia para escritorio y mobile sin contaminar la app de autenticación.
  • Hacer más claro el mantenimiento: auth y roles en usuarios, backoffice en gestion.

Diseño aprobado para Versión 2

Esta sección reúne definiciones ya acordadas que quedan fuera del MVP, pero forman parte del diseño aprobado para una segunda versión.

Alcance V2

  • Productos.
  • Variantes.
  • Pedidos.
  • Items de pedido.
  • Pagos de pedidos.
  • Movimiento de stock.
  • Reportes de ventas y stock.
  • Asientos simples vinculados a pagos.

Modelo de datos V2

Entidades V2: Producto, VarianteProducto, MovimientoStock, Pedido, ItemPedido, PagoPedido, Notificación, CuentaContable, Asiento, PartidaAsiento, BeneficioComercio.

Producto

Campos sugeridos:

  • id
  • nombre
  • descripción
  • precio
  • activo
  • controla_stock

Ejemplos: Remera Uni2, Apunte Matemática, Cuadernillo Inglés.

VarianteProducto

Campos sugeridos:

  • id
  • producto
  • nombre
  • sku
  • activo

Ejemplos: Talle S, M, L, XL para Remera Uni2; variante unica para apuntes.

MovimientoStock

Campos sugeridos:

  • id
  • variante
  • tipo
  • cantidad
  • fecha
  • descripción

Tipos: ingreso, egreso, ajuste, devolucion.

Decision: el stock se descuenta al entregar el pedido, no al crearlo ni al pagarlo.

Pedido

Campos sugeridos:

  • id
  • asociado
  • fecha
  • estado
  • estado_pago
  • total
  • observaciones

Estados: pendiente, en_preparacion, entregado, cancelado.

Estados de pago: pendiente, pagado.

Decisiones: no se permiten pagos parciales en V2 inicial, no se entregan pedidos impagos y no se cancelan pedidos entregados.

ItemPedido

Campos sugeridos:

  • id
  • pedido
  • variante
  • cantidad
  • precio_unitario
  • subtotal

PagoPedido

Campos sugeridos:

  • id
  • pago
  • pedido
  • importe

Relación futura: Pago 1 - N PagoCuota y Pago 1 - N PagoPedido.

Decision: se conserva un único modelo Pago para ingresos; PagoCuota explica cuotas y PagoPedido explica pedidos.

BeneficioComercio

Entidad futura para modelar múltiples beneficios por comercio o promociones con mayor complejidad.

Campos sugeridos:

  • id
  • comercio
  • titulo
  • descripcion
  • tipo_descuento
  • valor_descuento
  • condiciones
  • fecha_desde
  • fecha_hasta
  • activo

Notificación

Notificación interna del sistema.

Campos sugeridos:

  • id
  • usuario
  • título
  • mensaje
  • leída
  • fecha_creación

Notas: puede usarse como notificación interna; las push quedan para una versión futura.

CuentaContable

Cuenta utilizada para imputar partidas contables.

Campos sugeridos:

  • id
  • código
  • nombre
  • tipo
  • activa

Tipos: activo, pasivo, patrimonio, ingreso, egreso.

Asiento

Cabecera de un asiento contable simple.

Campos sugeridos:

  • id
  • fecha
  • descripción
  • tipo
  • importe
  • origen

Tipos: ingreso, egreso.

Notas: puede originarse en un pago de cuota y, a futuro, en otros tipos de pago.

PartidaAsiento

Línea contable perteneciente a un asiento.

Campos sugeridos:

  • id
  • asiento
  • cuenta_contable
  • movimiento
  • importe
  • detalle

Movimientos: debe, haber.

Reglas V2

  • RV2-001 No se permite crear pedido si no hay stock suficiente.
  • RV2-002 El stock se descuenta al entregar el pedido.
  • RV2-003 No se puede entregar un pedido impago.
  • RV2-004 No se permite pago parcial de pedidos en V2 inicial.
  • RV2-005 No se puede cancelar un pedido entregado.
  • RV2-006 Algunos productos pueden no controlar stock.
  • ASIENTO-001 Cada pago de cuota puede generar un asiento de ingreso.
  • ASIENTO-002 Todo asiento debe tener al menos dos partidas.
  • ASIENTO-003 La suma del debe debe ser igual a la suma del haber.
  • ASIENTO-004 El importe del asiento debe coincidir con el total balanceado de sus partidas.
  • ASIENTO-005 No se implementa contabilidad completa en esta etapa.

Casos de uso V2

  • CU-V2-003 Entregar pedido.
  • CU-V2-004 Ver estado de pedidos.

Casos borde V2

  • Pedido sin stock suficiente.
  • Intento de entregar pedido impago.
  • Intento de cancelar pedido ya entregado.
  • Producto que no controla stock.

Reportes V2
